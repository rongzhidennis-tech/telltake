# Easycut `state.sqlite` schema

This is the persistence contract for the `.easycut` package. The executable DDL
is in [`sqlite-schema.sql`](./sqlite-schema.sql) (migration 1) plus the numbered
migrations 2–7 in [`sqlite-migrations/`], applied in order
when a project is created or opened; the current schema version is **7**
(`0007_video_format`). `python3 scripts/check_schema.py` executes the whole chain.

Inside the app every database read and write runs on one serial queue
(`ProjectStoreIO`), so a transcription checkpoint and an editing read never
compete for the file lock. Each store call opens its own short-lived connection
with the default rollback journal and a five-second busy timeout, which only
matters when another process (a command-line tool) touches the same project.
**Back up project…** uses SQLite's online backup so a copy is always a single
standalone file.

## 1. Schema overview

The database is deliberately not an event-sourced project. It has directly
readable current state, immutable source and analysis history, materialized cut
plans, and append-only audit records.

| Layer | Tables | Contract |
| --- | --- | --- |
| Canonical mutable/current state | `project`, `source_clip_location`, `processing_stage`, `recommendation_review_state`, `cut_variant` (Creator Cut only), `cut_variant_segment` for editable cuts, `cut_variant_recommendation`, `project_state`, active `export_record` lifecycle fields | The current project can be opened and rendered from these rows without replaying history. |
| Immutable/versioned records | `recording_session`, `source_clip`, `source_relink_event`, `sequence_revision`, `sequence_membership`, sealed `transcription_run`, `transcript_version`, `utterance`, `utterance_source_range`, `word_alignment`, `non_speech_context_span`, sealed transcript correction revisions, sealed `analysis_run`, take-group records, sealed AI cut variants | Provenance and old results remain valid when a newer sequence, transcript, correction, or analysis is created. |
| Materialized/derived state | `non_speech_context_span`, `cut_variant_segment`, `cut_variant_recommendation`, `project_state` | Regenerable projections that make the current UI and render plan fast and deterministic. The cut plan is persisted because it is user-visible state, not a disposable cache. |
| Audit/history | `schema_migration`, `recommendation_review_event`, `edit_session`, `edit_operation`, completed/failed `processing_stage` attempts, `export_record` history | Explains what happened and supports undo/recovery. It is not required to reconstruct the current project. |

### Identity and units

- Domain IDs are UUID-style `TEXT` values generated by the application. SQLite
  row IDs are not used as domain identity.
- Timestamps are RFC 3339 UTC `TEXT` values, for example
  `2026-08-27T20:15:30.123Z`.
- Media-local time and durations are `INTEGER` microseconds. This avoids
  floating-point boundary drift in cuts.
- JSON columns are explanatory evidence or opaque provider metadata. They are
  not canonical relationships; relationships needed by the application have
  normal foreign keys.
- Every connection that can mutate or read the project must execute
  `PRAGMA foreign_keys = ON`. The DDL also sets it for the creating connection;
  SQLite foreign-key enforcement is connection-local.

### Lifecycle rules

1. A new project creates one `recording_session` and one `project_state` row.
2. Imported clips become immutable `source_clip` identities. Their current
   path, security bookmark, and availability are mutable in
   `source_clip_location`; relinking never changes the clip ID.
3. The creator confirms a `sequence_revision` before transcription. Its
   memberships are then frozen. Reordering or changing membership creates a
   new revision and requires new dependent transcription/analysis.
4. A `transcript_version` is an immutable transcription result. A correction
   creates a sealed `transcript_correction_revision` containing all current
   overlays. Analysis records the exact transcript and correction revision it
   consumed.
5. `analysis_run` output is immutable once sealed. A new transcription or
   correction creates a new run; old runs, recommendations, and AI cuts remain
   readable.
6. `ai_clean` and `ai_story` cut variants are sealed proposals. A `creator` cut
   is a mutable working cut made from the explicitly chosen parent cut. The
   baseline cut is never edited in place.
7. A current cut is rendered from its ordered `cut_variant_segment` rows. Any
   creator edit changes the segments, increments `cut_variant.state_revision`,
   updates the plan hash/duration, records an `edit_operation`, and updates the
   corresponding recommendation state in one transaction.

## 3. Constraints and invariants

### Enforced directly by SQLite

- Foreign keys are declared and `PRAGMA foreign_keys = ON` is required.
- Positive media ranges (`end_us > start_us`) and non-negative starts.
- Confidence/progress values, target ranges, ordinals, revisions, and byte counts
  are bounded by `CHECK` constraints.
- One recording session per project.
- Stable ordering within a sequence revision and unique clip membership within a
  revision.
- Unique utterance order within a transcript version.
- One correction overlay per utterance in a correction revision.
- One candidate recommendation per take group, with a composite foreign key
  preventing a candidate from being recommended for the wrong group.
- One clean and one story proposal per analysis run.
- One recommendation application row per recommendation per cut.
- One operation number per cut, enabling deterministic undo ordering.

### Enforced by transaction-level application invariants

SQLite cannot express every cross-row semantic rule with a simple table CHECK,
so the application must validate these before commit:

- All IDs in a run belong to the same project/session, sequence, and transcript
  context. The DDL keeps the direct FKs; the service verifies the parallel
  context IDs.
- A confirmed sequence revision is the only sequence used by its downstream
  transcription and analysis. A changed order creates a new revision.
- A correction revision contains all current overlays and its corrections point
  to utterances in its transcript version. Analysis must record the exact
  correction revision it consumed (or NULL for uncorrected text).
- `possible_alternatives` recommendations never enter an AI Clean Cut as an
  applied exclusion. Uncertain progression likewise cannot produce an automatic
  Clean Cut exclusion.
- AI Clean Cut automatically applies only high-confidence mechanical decisions;
  visual-only spans and standalone pauses remain included by default.
- Each Creator Cut has `origin_analysis_run_id` inherited from its parent cut,
  and `parent_cut_variant_id` equal to the explicitly chosen starting cut. The
  parent can be either the AI Clean Cut or AI Story Cut; the baseline is not
  modified.
- For a cut, segment `ordinal` is the rendered order, segments follow the
  confirmed source sequence, and all ranges are within their source clip. A
  segment’s `semantic_ref_id` is only an explanatory link; the concrete media
  range is authoritative for rendering.
- `cut_variant_segment.plan_revision` equals the containing cut’s
  `state_revision` after each successful edit. The writer updates both the cut
  row and its full segment projection in one transaction.
- `resolved_plan_hash` is computed from the ordered resolved segments and the
  relevant source identity/fingerprint data. Export records copy this hash so
  an output can be compared with the exact plan used to render it.

## 4. Key transaction examples

The examples use `:name` parameters and application-generated UUIDs/timestamps.
They show the boundaries; the application should validate semantic invariants
before executing the transaction.

### A. Confirm the inferred clip order before analysis

The inferred list is shown first. The creator’s accepted order becomes the
canonical revision for the run.

```sql
BEGIN IMMEDIATE;

INSERT INTO sequence_revision (
    id, recording_session_id, revision_number, status,
    source_sequence_hash, creation_reason, created_by, created_at, confirmed_at
)
VALUES (
    :sequence_revision_id, :session_id, :revision_number, 'confirmed',
    :sequence_hash, 'creator_confirmed_import_order', 'creator', :now, :now
);

-- Insert one row per imported clip in the confirmed order.
INSERT INTO sequence_membership (
    id, sequence_revision_id, source_clip_id, ordinal, membership_status,
    inferred_order_rank, order_confirmed_by_creator, ordering_evidence_json,
    created_at
)
VALUES (:membership_id, :sequence_revision_id, :clip_id, :ordinal, 'active',
        :inferred_rank, 1, :evidence_json, :now);

UPDATE project_state
SET current_sequence_revision_id = :sequence_revision_id,
    updated_at = :now
WHERE project_id = :project_id;

UPDATE project SET updated_at = :now WHERE id = :project_id;
COMMIT;
```

If the creator later changes order or membership, create another sequence
revision. Do not edit the frozen rows used by an existing run.

### B. Freeze transcript corrections and start analysis

The correction revision is a complete snapshot, not a patch that must be
replayed. The analysis run stores its exact revision ID.

```sql
BEGIN IMMEDIATE;

INSERT INTO transcript_correction_revision (
    id, transcript_version_id, revision_number, parent_revision_id,
    created_by, created_at, sealed_at
)
VALUES (:correction_revision_id, :transcript_version_id, :revision_number,
        :parent_revision_id, 'creator', :now, :now);

INSERT INTO transcript_correction (
    id, correction_revision_id, utterance_id,
    original_text_snapshot, corrected_text, created_at
)
VALUES (:correction_id, :correction_revision_id, :utterance_id,
        :recognized_text_at_edit_time, :corrected_text, :now);

INSERT INTO analysis_run (
    id, recording_session_id, sequence_revision_id, transcript_version_id,
    correction_revision_id, run_kind, analysis_configuration_version,
    model_provider, model_name, requested_at
)
VALUES (:analysis_run_id, :session_id, :sequence_revision_id,
        :transcript_version_id, :correction_revision_id, 'reanalysis',
        :config_version, :provider, :model_name, :now);

UPDATE project_state
SET current_correction_revision_id = :correction_revision_id,
    current_analysis_run_id = :analysis_run_id,
    updated_at = :now
WHERE project_id = :project_id;

COMMIT;
```

The run reads base text from `utterance.recognized_text` plus the frozen
correction rows. New corrections create a new revision and run; they do not
change this run.

### C. Materialize an AI Clean Cut and AI Story Cut

Clean analysis output is written as immutable take groups/recommendations. The
AI Clean Cut is then materialized. Only after the creator supplies the target
range does a separate `story_cut_generation` analysis run produce story-level
recommendations and the AI Story Cut. Each sealed proposal is committed as a
whole, so the UI never observes a half-built cut.

```sql
BEGIN IMMEDIATE;

-- Insert the Clean analysis take_group, take_group_candidate,
-- ai_recommendation, and target rows. Every such row references
-- :clean_analysis_run_id.

INSERT INTO cut_variant (
    id, project_id, recording_session_id, origin_analysis_run_id,
    parent_cut_variant_id, variant_kind, lifecycle_status, display_name,
    state_revision, resolved_duration_us, resolved_plan_hash,
    created_at, updated_at, sealed_at
)
VALUES (:clean_cut_id, :project_id, :session_id, :clean_analysis_run_id, NULL,
        'ai_clean', 'ready', 'AI Clean Cut', 0, :clean_duration_us,
        :clean_plan_hash, :now, :now, :now);

-- After the creator confirms the target range, insert a separate
-- story_cut_generation analysis run (:story_analysis_run_id), its
-- story-removal recommendations, and then the Story Cut. It is derived from
-- the Clean Cut, but its origin_analysis_run_id is the story run.
INSERT INTO cut_variant (
    id, project_id, recording_session_id, origin_analysis_run_id,
    parent_cut_variant_id, variant_kind, lifecycle_status, display_name,
    target_min_us, target_max_us, state_revision, resolved_duration_us,
    resolved_plan_hash, created_at, updated_at, sealed_at
)
VALUES (:story_cut_id, :project_id, :session_id, :story_analysis_run_id,
        :clean_cut_id, 'ai_story', 'ready', 'AI Story Cut',
        :target_min_us, :target_max_us, 0, :story_duration_us,
        :story_plan_hash, :now, :now, :now);

INSERT INTO project_state (
    project_id, current_analysis_run_id, current_ai_clean_cut_id,
    current_ai_story_cut_id, updated_at
)
VALUES (:project_id, :story_analysis_run_id, :clean_cut_id, :story_cut_id, :now)
ON CONFLICT(project_id) DO UPDATE SET
    current_analysis_run_id = excluded.current_analysis_run_id,
    current_ai_clean_cut_id = excluded.current_ai_clean_cut_id,
    current_ai_story_cut_id = excluded.current_ai_story_cut_id,
    updated_at = excluded.updated_at;

COMMIT;
```

In production code, insert `cut_variant_segment` rows before sealing the cut;
the shortened example omits the repetitive segment insert statements.

### D. Create a Creator Cut from the explicitly chosen starting point

The first manual change forks a new working identity. It copies the chosen
parent’s current materialized plan, but not its identity or baseline rows.

```sql
BEGIN IMMEDIATE;

INSERT INTO cut_variant (
    id, project_id, recording_session_id, origin_analysis_run_id,
    parent_cut_variant_id, variant_kind, lifecycle_status, display_name,
    target_min_us, target_max_us, state_revision, resolved_duration_us,
    resolved_plan_hash, created_at, updated_at
)
SELECT :creator_cut_id, project_id, recording_session_id,
       origin_analysis_run_id, id, 'creator', 'draft', 'Creator Cut',
       target_min_us, target_max_us, 0, resolved_duration_us,
       resolved_plan_hash, :now, :now
FROM cut_variant
WHERE id = :chosen_parent_cut_id;

INSERT INTO cut_variant_segment (
    id, cut_variant_id, ordinal, plan_revision, source_clip_id,
    source_start_us, source_end_us, semantic_kind, semantic_ref_id,
    created_at, updated_at
)
SELECT :new_segment_id_for_each_row, :creator_cut_id, ordinal, 0,
       source_clip_id, source_start_us, source_end_us, semantic_kind,
       semantic_ref_id, :now, :now
FROM cut_variant_segment
WHERE cut_variant_id = :chosen_parent_cut_id
ORDER BY ordinal;

INSERT INTO edit_operation (
    id, project_id, cut_variant_id, operation_number, operation_kind,
    actor_type, target_kind, target_id, before_state_json, after_state_json,
    created_at
)
VALUES (:operation_id, :project_id, :creator_cut_id, 1, 'create_creator_cut',
        'creator', 'cut_variant', :chosen_parent_cut_id,
        :parent_snapshot_json, :creator_snapshot_json, :now);

UPDATE project_state
SET current_creator_cut_id = :creator_cut_id,
    updated_at = :now
WHERE project_id = :project_id;

COMMIT;
```

The application supplies a distinct segment ID for each copied row; the SQL
uses `:new_segment_id_for_each_row` as a per-row binding placeholder.

### E. Apply one Creator Cut edit and persist undo state

A creator edit replaces the materialized range sequence, advances its revision,
and writes the audit operation in the same transaction. Undo later applies the
stored inverse snapshot as a new operation.

```sql
BEGIN IMMEDIATE;

-- 1. Read and lock the current Creator Cut at expected revision N.
-- 2. Validate the new contiguous utterance/range selection and compute:
--    :new_duration_us and :new_plan_hash.
-- 3. Replace cut_variant_segment rows with plan_revision = N + 1.

DELETE FROM cut_variant_segment WHERE cut_variant_id = :creator_cut_id;

-- Insert the complete new ordered segment sequence here.

UPDATE cut_variant
SET state_revision = state_revision + 1,
    resolved_duration_us = :new_duration_us,
    resolved_plan_hash = :new_plan_hash,
    updated_at = :now
WHERE id = :creator_cut_id
  AND state_revision = :expected_revision;

-- Require exactly one updated row; otherwise report a stale edit and ROLLBACK.
INSERT INTO edit_operation (
    id, project_id, cut_variant_id, operation_number, operation_kind,
    actor_type, recommendation_id, target_kind, target_id,
    before_state_json, after_state_json, created_at
)
VALUES (:operation_id, :project_id, :creator_cut_id, :next_operation_number,
        'edit_contiguous_range', 'creator', :recommendation_id,
        'utterance_range', :target_id, :before_json, :after_json, :now);

COMMIT;
```

The real implementation should use a savepoint or a staging table if the new
segment list is large, but it must retain the same atomic commit boundary. A
failed render can therefore never leave a Creator Cut with a new duration/hash
and an old segment list, or vice versa.

### F. Relink a missing source clip without changing identity

```sql
BEGIN IMMEDIATE;

INSERT INTO source_relink_event (
    id, source_clip_id, action, previous_path_hint, new_path_hint,
    observed_fingerprint, observed_fingerprint_algorithm, result,
    details_json, created_at
)
VALUES (:event_id, :source_clip_id, 'validation', :old_path, :new_path,
        :observed_fingerprint, :fingerprint_algorithm, 'matched',
        :details_json, :now);

UPDATE source_clip_location
SET local_path_hint = :new_path,
    availability_status = 'available',
    security_scope_bookmark = :bookmark,
    validated_fingerprint = :observed_fingerprint,
    validated_fingerprint_algorithm = :fingerprint_algorithm,
    last_checked_at = :now,
    last_validation_error = NULL,
    updated_at = :now
WHERE source_clip_id = :source_clip_id;

COMMIT;
```

The source clip ID and immutable original fingerprint remain unchanged. A
missing clip is represented by the same row with `availability_status =
'missing'`; the project can still open in review-only mode.

## 5. What is intentionally not in this v1 schema

- No full event log is required to open or render a project.
- No arbitrary word-deletion table: word timing is retained, while creator
  editing stays utterance/contiguous-range based.
- No speaker identity is required for the single-speaker launch scope.
- No server-side original-video storage is represented in project state. Upload
  jobs and temporary cloud artifacts belong in the processing service and are
  not required for local project recovery.
- No cross-analysis-run recommendation dismissal matching. `Ignore` belongs to
  the exact recommendation row from the exact run.
- No preference-learning labels: Creator Cut changes are recorded as feedback
  provenance, not automatic ground truth.

## 6. Genuine remaining schema ambiguities

These are implementation choices rather than reopened product decisions:

1. **Duplicate source imports.** The current UNIQUE constraint treats the same
   fingerprint imported twice into one project as one source identity. If the
   product needs two intentional references to the same bytes, replace that
   constraint with an import-instance table or allow duplicate `source_clip`
   rows.
2. **Cut plan segment granularity.** The schema permits arbitrary resolved
   source ranges and preserves semantic references, but the exact policy for
   snapping a boundary to a word, utterance boundary, or nearby pause is an
   implementation setting.
3. **Package-level deletion.** The schema supports referentially safe normal
   operations; deleting a whole `.easycut` package is best implemented as a
   package/file operation. If in-place row deletion is later required, define a
   tested archival/purge migration because historical runs are intentionally
   retained.
4. **Export artifact ownership.** `export_record` supports external outputs by
   default and package-contained outputs when the user opts in. A future sync
   design can decide whether to copy `exports/` without changing canonical cut
   state.
5. **Operational retry cardinality.** `processing_stage` retains retries as
   separate rows. The service may add a logical stage-run key if it needs a
   stricter “one active attempt per stage” invariant.

## Text-analysis usage evidence (ADR-102)

Take and Story `processing_stage.output_ref_json` envelopes optionally contain a
`requests` array. Records contain attempt/request/response identity, models,
configuration/transport/cache policy, byte counts, elapsed time, HTTP/provider
status, token categories, raw provider usage, price version and estimated USD.
A recorder writes an unconfirmed attempt before dispatch and replaces that attempt
with response metadata while the stage is running. Typed completion preserves it;
failure and cancellation leave it intact. This is provider evidence, not canonical
editing state, and requires no schema-v3 migration. Absence on older runs means
unknown usage, never zero cost. See [ADR-102](../decisions/ADR-102-compact-analysis-and-usage-accounting.md).

## Passage take candidates (schema 4, ADR-103)

Migration [`0004_passage_takes.sql`](migrations/0004_passage_takes.sql) adds:

- `passage_take_candidate`: canonical candidate ID, recommendation FK, ordinal,
  `is_preferred` boolean; one preferred candidate at most per recommendation.
- `passage_take_member`: candidate/utterance FKs and membership ordinal, unique
  candidate/ordinal and candidate/utterance pairs.

Recommendation targets remain the flattened ordered union for provenance. Source
ranges are resolved from immutable utterances; evidence contains original endpoint
IDs and unique-fact warnings. Before Clean materialization or passage editing,
normalized membership/preference must match that evidence. AI candidates never
change after sealing; Creator selection changes the cut projection and operation
history, preserving original preference. Existing single-utterance tables remain.

### Development retake removals (ADR-105)

Narrow development cuts reuse `clean_exclusion` recommendations with
`reason_code=verified_local_retake`; `details_json` stores the exact window, chain,
attempt and versioned boundary evidence. Applied links and normalized utterance
targets project the removal without mutating transcript timing. A separate sealed
AI baseline is materialized in a new project copy only.

`adjust_retake_boundary` operations reuse Creator plan snapshots and undo/redo.
`recommendation_review_event.details_json` version `retake-boundary-review-v1`
records original/adjusted source endpoints, unchanged-default acceptance, full
restoration and optional dialog elapsed seconds. These are boundary-review
observations, not content-correctness labels or proof of active human review time.
No schema migration is required.

### Migration 5: transcription evidence

`0005_transcription_evidence.sql` adds immutable raw provider response envelopes
per transcription run (`transcription_provider_evidence`) and ordered review
notes per utterance (`utterance_review_note`). Both are sealed in the same
transaction as the transcript. Invalid raw formatting timestamps remain in JSON,
not canonical word alignment. See ADR-106. No historical transcript is rewritten.

### Migration 6: durable transcription clip checkpoints

`0006_transcription_checkpoints.sql` adds `transcription_clip_checkpoint`, keyed
by run and source clip, storing immutable validated per-clip output JSON (text,
word/utterance timing, raw provider evidence, review notes), source identity,
input audio fingerprint, and creation time. This is canonical state, not cache.
The progressive adapter awaits the SQLite commit before starting another request.
Failed/interrupted runs retain checkpoints; an explicit retry copies matching
checkpoints into a new run, preserving original request evidence and ordering.
Reuse requires the identical sequence, provider/model/configuration/language and
source fingerprint/algorithm. Corruption fails closed without a silent paid rerun.

`transcription_clip_review_note` stores ordered clip-level review notes with the
sealed transcript, including successful no-speech outcomes. It does not create
fake utterances or grant cut authority. Speechless clips retain complete coverage
and a full-duration review row even below the usual two-second gap threshold.
Prior transcripts and project pointers survive migration unchanged.

### Migration 7: video colour format

`0007_video_format.sql` adds `video_codec`, `video_bit_depth`, `color_primaries`,
`color_transfer` and `color_matrix` to `source_clip`, recorded at import from the
container's format description (CoreMedia tag names such as `ITU_R_2100_HLG`).
The compatibility gate refuses to confirm a sequence that joins clips with different
colour signatures (bit depth or tags); codecs may differ because export re-encodes.
Export writes HDR or 10-bit sources as HEVC Main 10 with the source's tags and checks
the output carries them. Clips imported before this migration keep NULLs; a fresh
inspection is never required to match a value the project did not record, so older
projects confirm, preview and export as before.
